# 一次研究闭环与答辩表述

## 概念示例：研究评分机制

以下是说明调用链的假设场景，不是真实实验成绩，也不是随包提供的预选赢家。

外部图任务给出原始 `candidate.py`、训练图、成对样本和固定评价。AutoSpace 读源码后，可能提出改变 embedding-dependent scoring 的机制，声明训练正负样本与推断如何使用它、哪些参数接收梯度、与其他机制能否组合。

Critic 检查声明是否符合 `calculate_loss`、`predict`、`full_sort_predict` 的实际路径。若只改预测函数却声称影响训练和推断，就不是合格的完整机制。可行的规格进入 assembler 和机制池；这时只有假设，没有性能结论。

研究角色结合 frontier、正负反馈和未解决问题选择原语或兼容组合。Implementer 从冻结 root 生成完整代码。资格阶段检验接口与执行；worker 随后按固定数据、seed、训练规则完成训练，在共同开发集上选 checkpoint 并核验重载。

改善、回退和候选自身失败都会留下来源、代码、训练事实与成本，进入后继研究上下文。下一轮可继续检验、显式保留并组合其他机制，或转向其他假设。服务故障保留原请求与状态并协调恢复，不伪装成机制无效。

[离线演示](../examples/offline_walkthrough.py) 只用合成曲线演示反馈接口，并导入真实核心和 AutoSpace；不会伪造完整 LLM 研究或训练。

## 可直接使用的简短介绍

> RecClaw 面向推荐算法研究。它接收已有推荐模型和受约束的任务环境，先通过 AutoSpace 构造任务专属的可组合机制空间，再由研究角色提出假设、选择和组合机制、实现代码。候选经资格检查后进入真实训练与共同评价，指标、训练行为和失败证据回到后续研究中。我们关注从领域机制到代码再到实验反馈的闭环。不同模型通过任务适配器接入，训练和评价边界由外部环境保护。

> 当前系统已经形成这些源码与执行接口，但各实验冻结版本并不完全相同。我们分别说明功能实现、实际部署、开发观察和正式比较，不把空间审核通过当作提升，也不预设某种研究策略必定胜过对照。

## 常见问题

**与普通参数搜索有什么区别？** 研究对象包含模型计算、评分几何、目标函数等机制及组合，候选需要实现代码；允许修改仍受任务接口约束。

**空间是人为列好的吗？** 人工定义任务边界与比较条件。当前 AutoSpace 的机制内容由 Generator 根据任务事实提出，由 Critic 和 assembler 审核装配。历史静态空间仍在库中，但不是当前图 fresh AutoSpace 的来源。

**为什么同时有空间生成和研究闭环？** 前者回答“这个任务中可有意义地研究什么”，后者回答“现在最值得检验什么、如何实现、结果如何影响下一步”。空间质量和后续研究效果需分别检验。

**多角色就是有效性证据吗？** 角色分工是实现方式，需看是否产生忠实实现、有效实验和有用的后续决策，不能用角色数量证明能力。

**系统会不断学出更好的策略吗？** 当前图入口固定显式搜索策略，保留科研反馈与谱系。可说“下一轮读取实验结果”，不宜说“已证实在线元学习持续提升策略”。

**能否宣称跨模型普遍优于基线？** 架构或单个开发结果不足以支持。需分别核对源码、预算、独立重复、故障处理和受控 test；正式效果结论由对应实验材料支持。
